# 实验复盘

## 一、AI 承担的工作

| 环节 | AI 产出 | 人工参与 |
| --- | --- | --- |
| 需求建模 | 把一段自然语言需求拆成"请求层 / 解析层 / 持久化层"三阶段 | 确认阶段划分与验收标准 |
| 请求层 | UA 池、节流函数、Session 复用、重试与异常分支 | 补导入、指定真实站点、运行验证 |
| 解析层 | 卡片定位、四字段抽取、`urljoin` 转绝对链接 | 核对字段取值位置、确认只打印前 3 条 |
| 持久化层 | `DataFrame` 构造、`to_csv` 编码与索引参数 | 校验 CSV 行数、列序、Excel 乱码 |
| 文档 | README、用例、复盘初稿 | 逐条对照实验要求补漏 |

真实的协作节奏是"AI 出实现、人做验收"，AI 三分钟内能给出一份可运行代码，但**是否可交付由人工判断**。

## 二、人工审查与决策点

| 编号 | AI 给出的方案 | 审查发现 / 判断 | 处理方式 |
| --- | --- | --- | --- |
| D1 | 直接使用 `HTTPError`、`RequestException` | 未导入异常类，运行必抛 `NameError` | 追加 Prompt 只补导入，不改其它逻辑，保留迭代痕迹 |
| D2 | UA 池随机切换 | 随机 UA 会让同一会话指纹不稳定，对练习站点无必要但无害 | 保留，理由是降低单一 UA 被限流的概率 |
| D3 | 全局 `_last_request_at` 节流 | 用 `time.monotonic()` 而非 `time.time()`，避免系统时钟回拨导致间隔计算错误 | 保留，认可该实现 |
| D4 | 超时/连接错误重试 3 次，HTTP 错误直接放弃 | 404、403 属于确定性错误，重试无意义且加重站点负担 | 保留并写入测试用例 TC-07 验证 |
| D5 | `encoding` 为空或 `iso-8859-1` 时用 `apparent_encoding` | 国内新闻站常见 GBK 但响应头声明 ISO-8859-1，不修正会乱码 | 保留，认可为通用兜底 |
| D6 | `fetch_list_pages` 用生成器逐页 yield | 生成器避免一次性把所有页面 HTML 堆在内存，且便于失败页跳过 | 保留 |
| D7 | 价格保留 `£` 前缀、星级保留英文单词 | 作为原始数据留存合理，但后续做统计需要清洗 | 本阶段不处理，记入改进项 |
| D8 | 解析失败时返回空列表、不抛异常 | 会造成"静默失败"，抓取 0 条也看似正常结束 | 用"每页条数 + 总条数"两处输出兜住，记入风险项 |

## 三、风险识别

### 3.1 技术风险

1. **DOM 脆弱性**：四个选择器全部硬编码在代码里，站点改版即失效，且失效时不报错（返回空列表）。
2. **静默失败**：`all_books` 为空时仍会写出只有表头的 CSV，容易被误判为成功。
3. **编码依赖推断**：`apparent_encoding` 基于内容猜测，多语言混排页面仍可能误判。
4. **无结构校验**：没有"预期 20 条/页"这类断言，无法自动发现解析退化。

### 3.2 合规与工程风险

1. **站点规则**：本次目标站明确允许练习抓取；若换成真实新闻站，需先看 `robots.txt` 与用户协议，本项目的"2 秒间隔 + 受控页数"只是最低限度的礼貌策略。
2. **数据使用**：抓取内容仅用于课程实验，不二次分发、不做商用。
3. **IP 封禁**：固定出口 IP 高频抓取仍可能被封，重试退避只能缓解不能根治。

## 四、静态方案与动态方案对比（进阶挑战）

| 维度 | requests + BeautifulSoup（本项目） | 浏览器自动化（Playwright / Selenium） |
| --- | --- | --- |
| 适用页面 | 静态 HTML，数据在响应体里 | JS 渲染，数据由接口或前端运行时生成 |
| 实现复杂度 | 低，一个文件即可完成 | 高，需处理浏览器安装、驱动版本、等待策略 |
| 单页耗时 | 约 0.1–0.3 秒 | 约 1–3 秒，含浏览器启动与渲染 |
| 资源占用 | 几十 MB 内存 | 数百 MB 内存 |
| 稳定性 | 高，无渲染失败问题 | 受网络、页面脚本、超时策略影响 |
| 反爬对抗 | 弱，UA 与间隔即可 | 中，可模拟真实交互，但更易触发行为检测 |
| 维护成本 | 选择器一变即失效 | 同样依赖 DOM，还需维护等待与重试逻辑 |

结论：**先判断数据是否在初始响应体里**。静态页面用 `requests` 是显著更优解；只有在确认数据由 JS 生成（例如翻页走 XHR、列表为前端拼装）时，才升级到自动化方案。判断方法：`Ctrl+U` 看源码里有没有目标数据，或用 `requests` 抓一次看返回体是否含关键词。

## 五、可改进项（按优先级）

1. 增加结构校验：解析后断言"每页条数 > 0"，否则记为失败页并输出警告（解决静默失败）
2. 空数据显式提示：写盘前判断 `all_books` 为空，打印"本次未抓到任何数据"
3. 选择器外置：把 CSS 选择器抽到配置字典，站点改版只改配置不改逻辑
4. 数据清洗：价格去符号转 `float`，星级映射为 1–5 分，便于后续统计
5. 日志落盘：`logging` 增加 `FileHandler`，保留每轮运行的成功页数、失败页数
6. 重试加抖动：在退避时间上加随机偏移，避免多实例同时重试形成尖峰

## 六、结论

本次实验按"请求 → 解析 → 持久化"三阶段推进，每阶段都以运行结果作为门槛，没有出现"一次性生成完整爬虫再回头找 bug"的情况。AI 在单点实现上效率很高，但异常导入、静默失败、字段语义这类问题必须靠人工审查和真实运行才能发现。工程上真正拉开差距的不是"能不能写出来"，而是"出错时能不能被看见、被定位"。
