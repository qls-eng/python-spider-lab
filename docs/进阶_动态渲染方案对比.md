# 进阶挑战：动态渲染站点抓取的两方案对比

本文档对应指导书"进阶挑战"中的两项要求：**① 抓取一个动态渲染站点；② 对比两种实现方案的复杂度与效率**。
实验主链路（静态图书站 + 类重构）见 `实验报告.md`，本文档只记录进阶部分，属于实验完成后对照指导书补做。

| 项目 | 内容 |
| --- | --- |
| 完成日期 | 2026-11-18 |
| 目标站点 | `http://quotes.toscrape.com/js/`（Zyte 提供的引文练习站，公开免鉴权） |
| 新增文件 | `dynamic_crawler.py`（两种方案共 411 行，含公共请求层复用） |
| 实测环境 | Windows 11 + Python 3.14.5 + requests / beautifulsoup4 / websocket-client + 本机 Edge 157 |

## 一、为什么这个站点适合做"动态渲染"的样本

该站是专门给爬虫练习用的站点，页面上有引文卡片（正文、作者、标签），但 HTML 里**没有**这些卡片：

```text
状态码 200   HTML 长度 5806
div.quote 数量 0
含 var data 字样: True
```

即 `requests + BeautifulSoup` 拿到的是一副空壳：页面只带一段 `var data = [ ... ];` 的 JS 数组，前端 JS 读数组后才把卡片渲染进 `<div class="quote">`。
这正是"静态解析对动态页面失效"的最小可复现例子——**解析逻辑本身没错，错在拿不到渲染后的 DOM**。

## 二、方案 A：无头浏览器渲染

思路：让浏览器真的执行页面 JS，等卡片出现后再按 CSS 选择器解析 DOM。

实现要点：

- 浏览器以 `--headless=new` 启动，独立 `--user-data-dir` 临时目录，不触碰用户浏览器配置；
- 通过浏览器自带的 **DevTools 协议（CDP）** 驱动：`Page.navigate` 导航 → 轮询 `document.querySelectorAll('div.quote').length` → 命中后取 `document.documentElement.outerHTML`；
- 一个浏览器实例渲染多页，避免每页重启浏览器；退出时 `terminate` 进程并删除临时配置目录；
- 每页允许一次重试（首个页面要等 DNS / TLS / 外部 JS，网络抖动时首访容易超时）。

**为什么走 CDP 而不是 Selenium / Playwright**（这是本轮踩到的真实阻塞）：

| 方案 | 实测结果 |
| --- | --- |
| Selenium 4 | `webdriver.Edge()` 抛 `NoSuchDriverException`：Selenium Manager 需要联网下载 `msedgedriver`，本机下载失败 |
| Playwright | 约 40MB 轮子 + 浏览器运行时，镜像下载 5 分钟未完成，放弃 |
| 浏览器 `--headless --dump-dom` | 三种 headless 模式均**退出码 0 且 stdout 为空**，取不到 DOM |
| CDP 直连（最终采用） | 1.42s 启动完成，成功渲染 10 张卡片 |

结论：浏览器自带的 `--remote-debugging-port` 零驱动、零额外二进制即可完成渲染，代价只是一条 WebSocket 连接（`websocket-client`）。

## 三、方案 B：内嵌数据反查

思路：动态页面既然要在前端渲染，数据必然先到达客户端。定位这条数据通道比"追着渲染结果跑"便宜得多。

实现要点：

- 在 HTML 中定位 `var data = ` 标记，从其后的 `[` 开始用 `json.JSONDecoder().raw_decode()` 解析；
- 用 `raw_decode` 而不是正则匹配括号：数组内有嵌套对象、字符串里可能含方括号，正则切分会截错位置，`raw_decode` 从起始 `[` 解析到匹配结尾，天然处理嵌套；
- 拿到数组后直接映射成 `author / text / tags / page` 四字段，与方案 A 的解析结果同口径。

对应的线上形态就是**接口反查**：真实站点里这段数据通常来自一次 XHR / fetch 请求，只要在浏览器开发者工具里找到该接口地址，用 `requests` 直接请求接口即可，比解析 DOM 更稳、更省。

## 四、实测对比（同站点、2 页、同字段）

```text
============================================================================================
两种方案实测对比（同一站点、2 页、同样字段）
============================================================================================
方案              耗时(s)     条数      额外依赖                              环境准备
B 内嵌数据反查        5.00      20      无（仅 requests + BeautifulSoup）     无
A 无头浏览器渲染       19.96     20      websocket-client + 本机浏览器          无需下载驱动；需本机已装 Edge/Chrome

一致性核对：条数 B=20 / A=20，逐行字段（作者/正文/标签/页码）完全一致
```

同一份数据、同样 2 页（每页 10 条），两方案抓取结果**逐行完全一致**，说明方案 A 的渲染路径没有引入字段偏差。

> 耗时备注：上表是 2026-11-18 首次完整对比的记录。同一天稍后在清理掉无用依赖的环境里复测，得到 B 1.57s / A 6.54s——差异主要来自网络冷热与浏览器冷启动，**量级差异（约 4 倍）与"两者数据完全一致"的结论不变**。绝对秒数会随环境波动，比对时应以同一次运行的相对关系为准。

复杂度对比（代码量按 `dynamic_crawler.py` 实际行数统计）：

| 维度 | 方案 B 内嵌数据反查 | 方案 A 无头浏览器渲染 |
| --- | --- | --- |
| 核心代码量 | 53 行 | 158 行（浏览器类 109 行 + 解析编排 49 行） |
| 额外依赖 | 无（复用已有 requests + BeautifulSoup） | `websocket-client` + 本机 Edge/Chrome 运行时 |
| 单页耗时 | 约 2.5s（含 1s 节流），一次 HTTP 请求 | 约 10s（含浏览器启动与外部 JS/CSS 加载） |
| 资源占用 | 一个 HTTP 连接 | 额外一个浏览器进程（数十 MB 级） |
| 环境可移植性 | 换机器直接可跑 | 依赖浏览器路径与版本，需探测可用浏览器 |
| 稳定性风险 | 依赖页面仍内嵌数据；若改为纯接口请求则需改抓接口 | 依赖浏览器启动成功；CDP 时序、超时需调；版本升级可能影响参数 |
| 反爬对抗能力 | 弱（伪装程度与普通请求相同） | 强（真实浏览器指纹、完整 JS 执行） |
| 适用场景 | 数据以内嵌 / 接口形式下发（绝大多数前端框架站点） | 数据由 JS 计算生成、无法从请求侧拿到（加密签名、复杂拼接） |

耗时差异的构成：方案 A 的 19.96 秒里，浏览器启动约 1.4 秒，其余主要是页面本身要额外加载 bootstrap、CSS 与 JS，且是无窗口渲染模式下的冷启动；方案 B 的 5.00 秒里包含两次请求各自的 1 秒节流等待。**耗时约 4 倍差距，代码量约 3 倍差距，而两者拿到的数据完全相同**——这就是"优先找数据源、最后才上浏览器"的直接依据。

## 五、结论与选择建议

1. **先找数据源**：动态页面能渲染，数据就一定先到过客户端。定位内嵌数组或 XHR 接口（方案 B），通常是一次请求、零依赖、代码几十行就能拿全字段。
2. **浏览器是兜底手段**：只有当数据在客户端被二次加工（加密签名、多接口拼接、需要交互才有数据）时，才启用方案 A；本项目的站点两种都能做，方案 B 明显更划算。
3. **两者可以混用**：用方案 B 批量拿列表，个别需要交互才能展开的详情页再对方案 A 单点渲染。
4. **合规边界不变**：仅抓公开练习站点，无登录、无付费、无个人信息；请求间隔 ≥ 1 秒；不涉及验证码绕过与代理池。

## 六、复现方式

```bash
pip install -r requirements.txt          # 基础依赖
pip install websocket-client             # 仅方案 A 需要

python dynamic_crawler.py --strategy inline --pages 2    # 方案 B
python dynamic_crawler.py --strategy render --pages 2    # 方案 A（需本机 Edge/Chrome）
python dynamic_crawler.py --compare --pages 2            # 两方案对比 + 一致性核对
```

产物 `quotes.csv`（`utf-8-sig`，列：`author,text,tags,page`），与图书站的 `result.csv` 分开存放，不混淆两份数据。
